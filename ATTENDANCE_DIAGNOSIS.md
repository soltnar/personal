# Проходная: проверка 22.10.2026

Проблемные даты зависали в `ActivityFixation.GetPersonsMainEvents` на страницах 0/1. Старый загрузчик использовал страницы 1000 строк, два запроса по 25 секунд без успешного ответа. Одновременно тот же день иногда завершался за 1–2 секунды. HTTP 429 в проверенных сбоях не обнаружен: наблюдалось отсутствие ответа до тайм-аута, поэтому связь с ограничением 50 запросов в минуту не доказана.

Через Chrome DevTools снят локальный sanitized HAR `/tmp/saby-attendance-20261022.har`. Не добавлять HAR в Git: даже sanitized HAR содержит данные сотрудников. В интерфейсе Saby запрос за 19–20 октября имел размер страницы 30, HTTP 200, 312 мс. Сравнение с сервисным токеном с сервера, одна дата и одинаковый метод:

| Размер | CheckpointType | Organization | Результат |
|---|---|---|---|
| 30 | null | -1 | HTTP 200, 496 мс, 30 строк |
| 30 | 0 | -2 | HTTP 200, 148 мс, 30 строк |
| 200 | null | -1 | тайм-аут 6001 мс |
| 200 | 0 | -2 | тайм-аут 6001 мс |

Фильтры не были причиной в этих пробах; рабочие фильтры загрузчика оставлены без изменений. Размер страницы выбран 30, страницы последовательные с интервалом не менее 1,6 с (менее 38 стартов страниц за минуту на один загрузчик). Это не общий лимитер всех независимых интеграций сети. HTTP 429 завершает задачу, не вызывает немедленный повтор. Максимум страниц 200: при превышении день не отмечается готовым, чтобы не сохранять усечённые данные.

Полная загрузка с 30 строками затем встретила тайм-аут на странице 3. Повторная изолированная проба той же страницы через сервисный токен прошла за 434 мс; с SID — за 139 мс, через домен sbis.ru — за 137 мс. Поэтому уменьшение страницы само по себе не устранило все непостоянные зависания. Строго доказана нестабильность выполнения отдельных запросов; конкретную внутреннюю причину Saby (ограничение частоты, прогрев/кэш, серверный запрос) без их логов определить нельзя.

В закрытую таблицу добавлен `sync_progress`: исходные страницы, номер следующей страницы, подпись периода/размера/формата. Ошибка не удаляет прогресс; следующий запуск продолжает незавершённый день. Частичные страницы не видны отчётному API, день получает `ready` только после полного завершения. Для окна, включавшего текущую календарную дату, прогресс следующего дня сбрасывается, чтобы изменившаяся живая выборка не нарушила пагинацию. Принудительное обновление уже готового дня всегда начинается заново.

Cron отправляет задачи каждые 10 минут с 05:00 до 06:50 МСК; проверены запуски и HTTP 200. Статус cron `succeeded` означает постановку HTTP-запроса, а не завершение выгрузки. Фактический результат проверяется по `attendance_daily_cache.status`, числу событий, `error` и `updated_at`. Готовые дни автоматически не обновляются; пропуски и ошибки продолжают обрабатываться со следующего московского дня.

Диагностические HTTP-запросы запускались разово; расписание и сохранённая команда cron не изменялись. Временная диагностическая Edge Function закрывается после проверки.

Дополнительно снят HAR экспорта `/tmp/saby-attendance-export-20261022.har`. UI вызывает `Excel.SaveCustom` с `ActivityFixation.GetPersonsMainEventsExport`. Прямой вызов метода экспортера сервисным токеном не подтвердился (ошибки контракта/доступности метода), поэтому он не включён в ежедневный загрузчик как непроверенная замена.

Через встроенный Excel-экспорт Saby получено окно 19–22 октября. Файл содержит даты, время, источник, направление, ФИО, должность, подразделение, адрес и помещение. Для восстановления выбраны только «Проходная» и завершённые рабочие сутки 04:00–03:59. Дубли по времени, направлению, ФИО и помещению исключены. Восстановлены только строки кэша со статусом `error` и пустыми событиями: 19 октября — 649, 20 октября — 666, 21 октября — 620. Идентификатор сотрудника восстановлен из ранее готовых дней только при однозначном ФИО, иначе оставлен пустым (обычная группировка по ФИО). Исходный табельный номер сохранён отдельно; он не уникален между предприятиями и не подменяет Saby personId. У событий указан `recoverySource`. Готовые 17 октября (799) и 18 октября (753) не изменялись.

Ограничение проверки: восстановление через экспорт не доказывает успешный полный автоматический прогон нового загрузчика. Ежедневное расписание включено, защита готовых данных и продолжение страниц проверены тестами. Реальное завершение следующего автоматического дня ещё необходимо подтвердить.

При восстановлении обнаружена и исправлена ошибка преобразования направления: Saby использует `actionType=0` для выхода и `1` для входа. Изначально экспортер восстановления ошибочно записал выход как `2`, что создало массовые ложные предупреждения «нет отметки выхода». Исправлены только события с `recoverySource=saby-export-2026-10-22` за 19–21 октября: 327, 330 и 311 выходов соответственно. Количество и время событий не менялись. Проверка восстановления должна включать не только число событий, но и расчёт пар вход/выход, смен и предупреждений.

Схема закрытой таблицы дополнена применённой миграцией `attendance_sync_page_progress`:
```sql
alter table public.attendance_daily_cache add column if not exists sync_progress jsonb;
```
Промежуточные события доступны только сервисной роли. Пользовательский `personnel-report` выбирает готовые `rows` явно и не выдаёт `sync_progress`.
